# Notes for agents

- This is a static recomp of the PS2 game Road Trip (USA, SLUS-20398) using PS2Recomp (submodule `third_party/PS2Recomp`, pinned).
- **The built app must never contain game code.** The game is recompiled and compiled on the user's machine at first launch (`src/game/GameBuilder.cpp`), and `scripts/bundle_sdk.py` ships only the recompiler, runtime headers and config. Verify with `nm RoadTrip.app/Contents/MacOS/RoadTrip | grep -c sub_00`, which must print 0.
- **Never commit game data or derived code.** That covers anything under `generated/` and `build/`, disc images, ELFs, and extracted files. `.gitignore` covers them; check `git status` before committing.
- Pipeline: `python3 scripts/pipeline.py <steps> --rom <image>`. The steps are bootstrap, tools, extract-elf, analyze, recomp, build and run. `RT_ROM` can stand in for `--rom`.
- Recompiler config:
  - Edit `config/roadtrip.base.toml`.
  - `config/roadtrip.toml` is regenerated by `analyze`. It holds addresses only and is committed.
- Runtime/recompiler changes:
  - The submodule is the user's fork (silentsudin/PS2Recomp), branch `roadtrip`; remotes `origin` = fork, `upstream` = ran-j.
  - Commit there, push `roadtrip` (the user approved pushing this branch), then commit the bumped submodule pointer in this repo.
  - Generic fixes can be offered upstream as PRs; ask first.
- The app entry point is `src/main.cpp`. It runs setup (extract the disc, build the game dylib), then `rt::game::load`, then `PS2Runtime` initialize, loadELF and run.
- Debugging: `RT_THREAD_DUMP=5` dumps guest threads; `RT_FRAME_DUMP=<dir>` saves PNGs of the window every `RT_FRAME_DUMP_SECONDS` (from `RT_FRAME_DUMP_AFTER` seconds on) (needs a window, not `RT_HEADLESS`; headless, use the test socket's `frame` command, which reads the GS output); `RT_DEBUG_UI=1` shows the debug panel. To find where the game is stuck, attach lldb to the `GameThread` thread; the game functions are native, so they show up in the backtrace.
- Game hooks go in `src/game/overrides.cpp`.
- In-game menu (`src/ui/PauseMenu.cpp`, look in `src/ui/Theme.cpp`): Guide, Back+Start held 0.3 s, Esc, F3 or Android's back opens it and pauses the game (`ps2_test::setPaused`). The panel never changes size or position as the focus moves (picture rows only lift the scrim a little). Options live in `settings.toml` in the data directory (`src/settings/`); options a device can't use, or that aren't built yet, are hidden.
  - Screenshots headlessly: `RT_MENU_SHOT=<png> RT_MENU_PAGE=root|display|graphics|controllers|device|buttons|quit|reset RT_MENU_AT=<vblank>`; with `graphics`, `RT_MENU_ROW=<label>` selects that Options row.
  - Critics: have `choroq-style-critic` and `jobs-ux-critic` (`.claude/agents/`) review screenshots after UI changes.
- Agents in `.claude/agents/`: `bug-tester` (runs the regression suite, triages), `perf-profiler`, `reverse-engineer`, `release-guard` (run before commits/pushes), plus the two UI critics.
- Widescreen (Options → Aspect ratio, HUD position):
  - The game hook in `src/game/overrides.cpp` widens the 3D by narrowing the player cameras' projection X. It wraps 0x21F698 and its resume points, and keeps the tile-cull points (0x29CF40) widened.
  - The GS frontend's `WideLayout` (`gs_wide_layout.cpp` on the fork) narrows the HUD in driving frames, and marks 2D-backed screens, which the presenter shows at 4:3.
  - Frame boundaries come from the game's clear stub (`GS::markFrameStart`).
  - Unit test: `wide_layout_test`.
- Progressive fields (Options → Interlacing: Off, the default; `RT_PROGRESSIVE_FIELDS=0|1` overrides it):
  - The game draws 640x224 fields and moves every other one down half a line (sceGsSetHalfOffset at 0x26F340 and 0x26F3C8, `halfoff` = the field parity). The hook in `overrides.cpp` forces `halfoff` to 0.
  - The pgs backend hides INT/FFMD from paraLLEl-GS, so the field is scanned out as a progressive double-strike picture.
  - `VSyncInfo::progressive_field_scanout` takes twice as many lines as columns from the super-samples: 2x and 4x give 640x448, 8x and 16x give 1280x896 (`shaders/scanout_sampling.h` on the paraLLEl-GS fork).
  - A real 448-line frame can't fit in VRAM: textures start at block 0x1A40, right after the 224-line buffers and Z.
  - The regression harness pins `RT_PROGRESSIVE_FIELDS=0` so the goldens keep the original fields; `test_progressive_fields.py` covers the progressive path.
- Texture dumps and HD packs (Options → Texture pack; `[textures] dump` and `pack_anisotropy` in settings.toml, for pack makers and tuning; `gs_texture_tools.cpp`, the pgs backend's `textureToolsLocked`, and the readback/prediction hooks in our paraLLEl-GS fork):
  - a texture is the whole image the game uploaded (host-to-local transfer at the TEX0 base, same format), not the part a draw samples: the game cuts sprites out of atlases with REGION_CLAMP (the HUD font is one 512x384 4-bit upload). With dumps or a pack on, paraLLEl-GS tracks uploads (`GSInterface::uploads`) and decodes a REGION_CLAMP draw inside one as the whole upload (`decode_desc`, its own cache key, no sampler feedback), while the draw keeps its own descriptor and sampler region. Widened draws skip the render-pass texture memo, which the image's invalidations can't reach. A draw over pages the game has rendered to isn't widened. `test_texture_pack` checks that dumping changes no pixel.
  - with either on, paraLLEl-GS copies each newly decoded texture (RGBA8 with the palette applied; PS2 alpha, 0x80 = opaque) back to the host. A worker names it by an FNV-1a hash of its decoded pixels: the same texture gets the same name across runs, wherever it sits in GS memory, and a palette swap is a different texture.
  - dumps go to `<data>/textures/dumps/<hash>_<W>x<H>_psm<NN>.png`. A pack is a folder in `<data>/textures/packs/` of PNGs whose names start with the 16-digit hash, at any size (alpha in PNG terms).
  - a replacement is created once per content (sampled only, no storage usage: paraLLEl-GS addresses it by the original texture's size and keeps it out of its image pool). It is bound by the texture's stable key (the cache key without the palette instance, `TextureDescriptor::stable_key`), because Road Trip reloads palettes every frame and paraLLEl-GS decodes such textures under a new cache key each time. Each decode still reads back and re-checks: a description that decodes to something else drops its prediction.
  - replacements get a full mip chain and are sampled with analytic texture-coordinate gradients through a trilinear/anisotropic sampler (`BINDING_SAMPLER_ANISO`, the `TEX_INFO_REPLACED` path at the top of `sample_texture` in `ubershader.comp`). `pack_anisotropy` sets it (1–16, default 16; no menu row: it costs next to nothing).
  - `RT_TEXTURE_DUMP=<dir>`, `RT_TEXTURE_PACK=<dir>` and `RT_ANISOTROPY=<n>` override the settings. Headless, the GIF path services the readbacks when no vsync has for 50 ms.
  - clamped textures sample through clamp-to-edge variants of that sampler (bindings 27–29), so pack images don't bleed in their far edge at any mip level.
  - switching packs (or to none) drops every replacement and prediction on the main and shadow GS and invalidates the whole texture cache (`GSInterface::drop_texture_replacements`), so textures decode from GS memory again. The Texture pack hint shows how many of the pack's images the game has used (`PgsControl::texturePackStats`).
  - HD packs (the main use: every dump upscaled): replacement images are created at most 24 MB per frame (`kCreateBytesPerFrame`, pending ones wait), and kept within a memory budget (2 GB, `RT_TEXTURE_PACK_BUDGET_MB`): paraLLEl-GS reports the replacements it binds (`collect_used_replacements`), and images not drawn for 2 s are evicted oldest first down to 80%, then the texture cache is invalidated once (predictions rebind the rest at once). A 4x pack of every dump (6,499 images, 13 GB if all resident) holds 60 fps in a race with 254 images, 1.25 GB; loads cost up to ~4 ms a frame. `[textures] pack:` log lines every 5 s give images, MB, pending, evictions, worst ms per frame and palette matching.
  - other palettes of a replaced paletted texture (fades, flashes: Road Trip reloads palettes, and paraLLEl-GS keys by register state, so a fade keeps the stable key): `TextureTools` keys paletted textures also by index pattern (colour classes by first appearance) and, on a miss, fits an affine colour map (4x4 + offset, least squares, within 3 levels) from a replaced texture with that pattern to this palette. The pack image is then bound with `TEX_INFO_RECOLOR`, the map in the `texture_recolor` UBO (binding 30, slot in TexInfo flags >> 8). Arbitrary palette swaps don't fit and need their own pack image (they are dumped). `RT_TEXTURE_RECOLOR=0` turns it off; `RT_TEXTURE_RECOLOR_TEST=swap` recolours every match red/blue swapped (test hook).
  - `rt_audio_extract <disc dir> <out dir>` (`tools/audio_extract.cpp`) decodes the disc's VAG streams (PlayStation ADPCM) to WAV, `_L`/`_R` pairs as stereo: SOUND/1CH-3CH, about an hour each at 12 kHz (1CH's channels are identical). The sequenced music and effects (TSQ sequences + TVB sample banks, Takara's own formats, played by SNDMOD.IRX) are not decoded.
  - `rt_texture_extract <disc dir> <out dir>` (`tools/texture_extract.cpp`, `src/textures/Extract.cpp`) writes every texture on the disc in seconds, under the same names: it replays each file's GS upload packets (BITBLTBUF..TRXDIR + IMAGE) into a GS memory image (PS2Recomp's `ps2_gs_memory.h`) and decodes them as paraLLEl-GS does (`upload.comp`: CSM1 palettes, 16-bit colour `<< 3`, TEXA with AEM on, which is what Road Trip sets). A texture's palette is the one a TEX0 in the file names, else the upload right after it. A 256-colour palette after a 4-bit texture gives 16 banks (CSA); banks other than 0 go to `palette-variants/`. `sources.csv` says where each came from. Textures the game builds or recolours in code (HUD colour flashes, palette fades) are only caught by runtime dumps.
  - `test_texture_pack.py` dumps a race, makes a tinted 2x pack from those dumps in a temp dir, and checks that the pack shows, goes and comes back when switched while running, and that anisotropy changes it.
- Hardware GS (`RT_GS_BACKEND=hw`, `include/runtime/gs/gs_hw_backend.h`, `src/lib/gs/hw/` on the fork): draws the frontend's primitives with the Vulkan graphics pipeline on the presenter's device (or its own, headless), for what Road Trip does, not the whole GS. Lighter than emulation is the goal (`build/scratch/hwgs/baseline.md`: ARMSX2 vs us on the Thor).
  - Spec: `RT_GS_STATE_SURVEY=<file>` (`%p` = pid) counts every distinct draw state and transfer; `scripts/hwgs_survey.py` runs the suite with it and writes `build/scratch/hwgs/states.md`.
  - Render targets stay on the GPU (RGBA8 at the render scale, vertical scale doubled for progressive fields, alpha stored as A/128 so As/Ad blend factors are exact); one D32F depth image per ZBP. Textures are decoded on the CPU from local memory (palette applied, cached by page versions + palette); a texture inside a render target (the post-pass, the loading blur) samples a snapshot of it; DATE reads that snapshot at the pixel.
  - The GS thread records and submits at buffer flips; `Present` records the rest and scans out. Consecutive draws merge when the frontend's draw-state serial (`GSPrimitiveBatch::stateSerial`, bumped by any non-vertex register write) is unchanged, else when `sameDraw()` finds the states equal field by field (never memcmp: padding holds garbage). Vertex data goes through a ring of 8 fenced buffers; uploads are hashed per page, so re-uploading the same pixels (the game does it every frame) invalidates nothing. Alpha test and alpha mode are specialization constants. Render scale: the supersampling setting (1/4/16 = 1x/2x/4x); `RT_GS_SCALE=<n>` wins over it. `RT_HWGS_STATS=1` logs batches, passes and snapshots per present and what breaks batches.
  - Shaders: `hw/draw.vert|frag`, rebuilt into `hw_spirv.h` by `hw/compile.py` (glslc).
  - Texture dumps and packs (`hw/gs_hw_textures.cpp`, `HwTexturePacks` over the same `TextureTools`): with either on, each batch's texture is named as paraLLEl-GS names it (`effectiveRect`, the port of `compute_effective_texture_rect`; a REGION_CLAMP draw inside a tracked upload stands for the whole upload) and decoded on the CPU once per content for the tools. A race dumps every name paraLLEl-GS dumps (281 of 281) plus a few it skips (the 640x448 title picture), so packs work on both. A replacement is drawn with `F_REPLACED` (implicit derivatives, the anisotropic samplers, clamped axes clamp to the edge) and recoloured with `F_RECOLOR` (the map in the binding-2 UBO). Settings, results and image creation are serviced at Present, or from the GS thread after 50 ms without one (headless). Eviction and the `[textures] pack:` line go by wall time (2 s unused, every 5 s). Switching packs or evicting resubmits textures; the decoded cache stays.
- VU1 microcode is recompiled to lean code (the default; the game builder passes `--split`: one function and file per microprogram, which compile in parallel and in linear time, where one function of all eight took minutes on a phone): straight-line code per explored node, stalls as constants, Q/P landing where the explorer saw them, flags only where read, an XGKICK copies the packet at the kick; it deopts to the interpreter when timing isn't static. `vu1_replay` checks it against the interpreter (`--split`, `--reference-interp`). `PS2X_VU1_RECOMP_FLAGS="--interp-steps"` (read by `ps2_vu1_recomp`, so through the game builder too) builds the previous interpreter-step code for A/B.
- The GIF/GS hand-off reuses packet buffers (`GifArbiter::recycle`), and a waiter is woken only when the lowest target it waits for is reached. Its queue ordering allocates nothing when already in order (`std::stable_sort`'s buffer after every VU1 program cost a tenth of the VU1 thread on Android, in malloc's lock).
- Interlace flicker blending can be turned off with `RT_FLICKER=0`.
- Supersampling above 4x needs 8/16-wide compute subgroups. paraLLEl-GS's `fixed_wave32()` allows it on Apple GPUs, where MoltenVK reports sizes 4..32 but compute runs 32 wide. The `[gs]` log line shows the rate in use and the maximum.
- Performance overlay (Options → Performance overlay, `[general] performance_overlay`): `src/ui/PerfOverlay.cpp` draws one row along the bottom edge (clear of the race HUD) from `src/debug/PerfStats.cpp` (half-second windows: fps, worst frame, VU1/GS busy, app CPU via getrusage; on Android GPU busy and clock from kgsl sysfs and battery temperature).
- Second screen (Android dual-screen devices such as the AYN Thor; Options → Second screen, `[general] second_screen`, shown only when a presentation display exists):
  - `RoadTripActivity.java` shows a `Presentation` with a SurfaceView on the first presentation display; its surface and touches reach native code through `src/platform/SecondDisplay.cpp` (JNI), and `setSecondScreenEnabled` hides it again.
  - The Vulkan presenter (`setSecondScreen`, `gs_pgs_presenter.cpp` on the fork) keeps a second swapchain on the same device (MAILBOX, non-blocking acquire, presented after the main frame) and draws a second ImGui context the app renders (`submitSecondScreenUi`). UI textures: `createUiTexture` (nearest optional), `kPictureTexture` (the scanout) and `kMapTexture`.
  - The game's map: with `PgsShared::wantMap`, the hardware GS draws every map batch (TEST_2 = 0x3380B, plus the town bezel sprites; `[map]` in `config/game_state.toml`) into its own opaque layer instead of the frame, and publishes the map's box (bezel excluded) and shape; the map then leaves the top screen. paraLLEl-GS doesn't separate it (no Map page content there).
  - `src/ui/SecondScreen.cpp`: tabs Map / Notebook (context picks one: map while driving or racing, notebook in menus; a tap overrides until the context changes; choosing Notebook gives the map back to the top screen) and a Menu pill. Map page: the map plus a column (race: course, lap, last lap against the best, best lap; town: name, time, houses to visit, coins). Notebook: name, chips (licence, money, coins, towns), Got / To get stamp cards with the game's stamp art (decoded from `SYS/STAMP.GSL` on the user's disc) and captions (read from the ELF in RAM).
  - Game state for it: `src/game/GameStats.cpp` (addresses mirror `config/game_state.toml`: progress fields, `[game]`, `[race.live]`).
- `RT_GS_BATCH_LOG=<file>` logs every GS draw batch (path, prim, texture, bounding box), used to tell the HUD from the 3D scene.
- Platform layer is SDL3 under raylib 6.0 (`PS2X_HOST_PLATFORM=SDL3`, set by the app; the fork defaults to GLFW for upstream).
- Input:
  - `src/platform/input/` maps the keyboard and SDL3 controllers to the game's two pad ports, with `input.toml` v2 in the data directory (v1 files are migrated).
  - Players: keyboard + first controller = P1, second controller = P2. P2 is unplugged until a device is assigned.
  - The game's vibration (scePadSetActDirect) plays on that player's controllers.
  - The in-game menu's Controllers page handles assignment, rebinding, deadzones and rumble (`src/platform/Controllers.h`).
  - Unit tests: `build/macos-release/input_test` (ctest `input`), including a virtual SDL controller.
  - Pad families (`padFamily`): PlayStation keeps the game's layout; Xbox-style (anything else, including the Thor's pad) and Nintendo pads confirm with A and go back with B (`familyProfile` moves the face buttons for devices without their own bindings; our menus follow). On the hardware GS, `src/ui/ButtonGlyphs.cpp` repaints the game's ○ ✕ □ △ / L1..R2 glyphs with the pad's letters through the backend's decode hook (`PgsControl::setDecodeHook`; `RT_GLYPH_FAMILY=xbox|nintendo|ps` forces one, `RT_GLYPH_DEBUG=1` logs the atlas match).
  - Test socket `sdlpad` (`AndroidGame.sdl`) drives a virtual SDL pad. Lockstep's test pad overrides SDL input to the game, so check game input from it in real time (`lockstep=False`), holding ~0.4 s.
  - `scripts/check_android_input.sh` checks that the input layer builds for Android arm64 (needs the NDK; Homebrew's `android-ndk` works).
- Pads in the runtime and tests:
  - `RT_PAD_TRACE=1` logs the game's pad commands.
  - Test socket: `pad`/`step` take `"port"` (else both ports) and `"connected"`; `actuators` and `pad_info` report per port.
  - The app adds its own test-socket commands through `ps2_test::setCommandHandler` (`src/main.cpp`): `{"cmd":"texture_pack","path":DIR}` switches the pack ("" = none; without `path` it only reports `pack_images` and `replaced`).
  - Movies are version 2 (port column, `# connect` lines); v1 movies drive both ports.
- The GS renders on paraLLEl-GS/Vulkan (`ps2xRuntime/src/lib/gs/gs_pgs_backend.cpp` on the fork) by default; `RT_GS_BACKEND=cpu` switches to the software GS for A/B comparisons. Use `RT_FRAME_DUMP` to compare frames from the two.
- paraLLEl-GS is our fork: silentsudin/parallel-gs, branch `roadtrip` (remote `upstream` = Arntzen-Software). Its shaders are precompiled: after editing `gs/shaders`, run `scripts/regen_pgs_shaders.sh`, which builds slangmosh into `build/tools` the first time.
- Presentation goes through `ps2x::HostPresenter` (`ps2_host_presenter.h` on the fork):
  - the default is an SDL3 window with a Granite swapchain on the paraLLEl-GS device, so the picture stays on the GPU and ImGui is drawn through Granite (`gs_pgs_presenter.cpp`);
  - `RT_PRESENTER=raylib` (also the default with `RT_GS_BACKEND=cpu`) uses raylib/OpenGL, which reads the picture back every frame;
  - perf numbers are in `build/scratch/perf/vulkan2.md`: half the main-thread CPU, 60 fps held;
  - post-processing (Vulkan presenter only):
    - FXAA, SMAA, AMD FSR 1 and MetalFX spatial, in `gs_pgs_presenter.cpp`;
    - the shaders are in `src/lib/gs/post` on the fork; rebuild `post_spirv.h` with its `compile.py` (needs glslc);
  - temporal inputs from the game:
    - **depth** is the GS's Z scanout, snapshotted where the 3D ends;
    - **per-object motion vectors** come from `gs_motion.cpp`: VU1 matrices per object, re-projected per vertex, carried in paraLLEl-GS's `VertexPosition.padding`. They feed TAA and MetalFX temporal. MetalFX temporal needs a progressive picture (progressive fields, or 4x SSAA and up with interlaced fields) and uses MetalFX spatial otherwise. It scales at most `maxScale()` per axis (3x on the M3 Max); the presentation's bilinear pass scales the rest, and a scaler that can't be created is logged as `[metalfx]`;
    - the camera **jitter** comes from the game hook;
    - the **UI mask** (HUD and 2D screens, so only the 3D is post-processed) comes from the HUD classifier;
    - debug views: `RT_SHOW_DEPTH=1`, `RT_SHOW_MOTION=1`, `RT_MOTION_DEBUG=1`.
  - guest vblanks can be phase-locked to the display on 60/120/240 Hz screens (CVDisplayLink; off by default since present-at-time, `RT_DISPLAY_LOCK=1` turns it on, `RT_DISPLAY_LOCK_DEBUG=1` logs the phase error). Measurements: `build/scratch/perf/run_dl.py` (xctrace on-glass intervals).
  - present-at-time (`VK_GOOGLE_display_timing`, which MoltenVK maps to Metal's presentAtTime): the presenter wraps Granite's `vkQueuePresentKHR` and aims each present at a fixed grid of refreshes, one present every refresh-rate ÷ present-rate refreshes, with an adaptive lead (2 ms to one refresh; `RT_PRESENT_DEBUG=1` logs it). Left alone, presents land anywhere in a refresh, and on a 120 Hz ProMotion panel frames alternate between 1 and 3 refreshes (judder); macOS ignores a preferred 60 Hz frame rate. `RT_PRESENT_AT_TIME=0` turns it off. `RT_PRESENT_EVERY_REFRESH=1` repeats frames on every refresh instead, but costs the GS frames, because the presenter waits for swapchain images under the shared device lock (Granite's present-wait latency is 2, or 3 with frame generation).
  - frame generation (Options → Frame rate 120/240; re-rendered by default): shadow paraLLEl-GS instances (`gs_pgs_backend.cpp`) record everything mirrored between vsyncs, with PATH1 3D re-projected by `MotionTracker::packetReproject` at matrices moved on by part of a frame. A worker replays it after the real frame, in 0.5 ms slices under the device lock, flushing before each release. The result is shown between real frames with no added latency. `RT_FRAME_GEN=1` adds the picture-warping modes (`post/frame_gen.frag`) for comparison. Shadow frames keep HUD vertices in place (classifier UI class) and take the HUD from the real frame through the UI mask. A whole object whose screen motion exceeds 200 px is not moved. With TAA a shadow frame blends with the real frame's TAA output reprojected half a frame (not written back as history); MetalFX temporal runs a second scaler with its own history for shadow frames. The MetalFX passes do not wait on the CPU: they are encoded on MoltenVK's Metal queue after the presenter's submit (a fence wait under the device lock held the game at 30 fps at 120 Hz). Asynchronous MoltenVK submits (`MVK_CONFIG_SYNCHRONOUS_QUEUE_SUBMITS=0`) lose the device: don't.
  - objects are matched to last frame's (`MotionTracker::matchPrevious`): the object at the same draw position if it is within 3 world units, else the nearest within 3 units, with orientation breaking ties. Measured at a race start: draw order is stable for 93% of objects, which move 0.5-0.75 units a frame; grid cars stand 10-30 units apart, a car's wheels sit 0.7-1.4 units from its body and turn a long way each frame. A 40-unit radius mixed up neighbouring cars and a car's own parts. Shadow frames keep Z as the game computed it, so coplanar decals keep equal depths.
  - interlace flicker blending (progressive fields only, `post/flicker.frag` and `flicker_cut.frag`): pixels that alternate between two pictures, and hard cuts, are blended as an interlaced TV would show them. The loading screen alternates the blurred menu and black every frame.
  - on macOS the Vulkan presenter presents through Metal (`gs_metal_present.mm`): it renders into an offscreen BGRA8 backbuffer (a ring of three) under the device lock, then, after releasing the lock, copies it into a drawable of the window's `CAMetalLayer` on MoltenVK's own Metal queue, with `presentDrawable:atTime:`. Presented handlers feed the adaptive lead. MoltenVK's swapchain fetched its drawable lazily under the lock the GS needs, and at two presents per frame that cost game frames. `RT_METAL_PRESENT=0` uses the Vulkan swapchain, as other platforms do.
  - the app reaches the window, keys and time only through `src/platform/Host.h` (SDL3), so both presenters work.
- Runtime data lives in `~/Library/Application Support/RoadTripRecomp/{disc,saves}`. Override the location with `RT_DATA_DIR`.
- Boot ELF facts: entry 0x200008, SHA-1 2431de1e…, CRC32 0x5A49851D.
- Disc images: `IsoReader` reads .cue/.bin, .iso and .chd (libchdr, FetchContent; CD and DVD CHDs, the data offset found by the volume descriptor at sector 16). A picked image is hashed whole against the good dump (`verifyImage`, `RomInstaller.h`; Redump disc 27678 lists the .bin's SHA-1): .bin 236b902a…, .iso (its 2048-byte sectors) 62a9b61f…, CHD data 3db60fb0… (`chdman createcd` from the .bin) or the .iso's hash (`createdvd`). A CHD is decompressed in full (libchdr checks each hunk's CRC) and compared with its own header record first: damaged = mismatch, intact but made another way = unverified. Mismatch/unverified asks before going on (Android: "Use it anyway"); `--rom`/`RT_ROM` only logs it. The boot ELF check stays the hard gate. `iso_reader_test` (ctest, `RT_ROM=<image>`) covers all four forms.
- Third-party licences: `scripts/collect_licenses.py <build dir> <out>` gathers every shipped component's licence (fails on a missing one) into the Mac bundle's `Resources/licenses` and the APK's `assets/licenses` (with LLVM). Note paraLLEl-GS is LGPL 3 and libdwarf (in the recompiler, linked into the Android app) LGPL 2.1.
- The GIF/VIF1 worker hands GS batches to the GS thread every 24 packets while VU1 runs (`PS2Memory::drainGif`), so VU1 and GS overlap; the game, VU1 and GS threads run at user-interactive QoS. `RT_GS_OVERLAP=0` restores one batch per VIF1 job. At 60 Hz a frame had only about 1 ms of headroom before.
- Regression suite: `python3 scripts/regress.py [-n 4] [-k ...]` (tests/regression, pytest). Run it before committing runtime/recompiler changes. Golden images and checkpoints live in build/regression and must never be committed; only hashes (goldens.json) and inputs are.
- `RT_TEST_RENDER_ALWAYS=1` makes the regression harness draw every frame instead of only around pictures (goldens then differ). With `RT_TEXTURE_DUMP=<dir>` it dumps every texture a suite run shows, including the ones the game builds in code.
- Android (branch `android-port`, tested on the AYN Thor, Adreno 740):
  - `scripts/android/build_llvm.sh` cross-builds the on-device compiler (`libllvm.so`, clang + lld, LLVM 21 to match the NDK); `scripts/android/build_apk.sh [--release] [--install]` builds `libmain.so`, the build kit (`bundle_sdk.py --android` → `assets/rt.tar`) and the APK (`platform/android/`).
  - The app recompiles and compiles the game on the device (`GameBuilder.cpp`, Android branch) into `files/game/libroadtrip_game.so`.
  - First run (`src/ui/SetupScreen.cpp`, drawn through the Vulkan presenter opened early, `setupPresenter()` in `main.cpp`, then handed to the runtime): a welcome screen, the system document picker (`SDL_ShowOpenFileDialog`; `IsoReader` reads the picked `content://` URI through the content resolver), then the setup screen: step, bar, percentage and time left. Compile units are weighted by measured cost (Thor: 2.4 s + 11.7 µs/byte of game code, VU1 parts 10x per byte; the `[build]` log lines give per-unit times), compiled heaviest first, and the time left comes from how fast a worker gets through weight (`TaskProgress::unitSecondsLeft`). A first-run compile on the Thor takes about 2.5 minutes. The disc check is step 1 of 5; an image that doesn't verify gets its own screen (looks different / damaged / a .chd that can't be checked, which defaults to "Use it"); a failure offers "Try again" (re-runs the task) and "Close". Buttons take a tap, or focus (gold rim, horn) moved with the D-pad/stick/arrows and A/Start/Enter; the panel is at most 1.2x the screen height wide. Compiling carries on while the app is in the background. `RT_REBUILD_GAME=1` rebuilds (env.txt stands in for `--rebuild-game`); `RT_SETUP_TEST_FAIL=1` shows the failure screen.
  - RT_* switches come from `files/env.txt` (`run-as io.github.roadtrip.recomp`); logs: `adb logcat -s RoadTrip`.
  - Tests: `tests/regression/rtharness/android.py` `AndroidGame` (test socket over `adb forward`, inline frames, `sdl(...)` presses a virtual SDL gamepad; `lockstep=False` for real time).
  - Adreno: sampler feedback off (`RT_PGS_NO_FEEDBACK=0|1` overrides), one precompile thread; `RT_PGS_TIMESTAMPS=1` logs GPU ms per stage.
  - Adreno also: the hierarchical binner is off (it loses blocks of tiles, as on Metal; `RT_PGS_HIER_BINNING=0|1`), and trilinear filtering is one hardware fetch (`RT_PGS_HW_TRILINEAR=0|1`): the ubershader runs at 12-18% occupancy there, so each dependent texture fetch is exposed (shading 45.6 → 18.1 ms in the demo). The texture-pack path is compiled into the ubershader only when a pack texture is bound (every GPU). Profiling notes: `build/scratch/android/adreno_perf.md`.
  - `RT_TEST_LIVE=1`: the test socket runs without lockstep (real time; the app menus work).
  - Background (home, another activity, screen off): `src/platform/Lifecycle.cpp` pauses the game (unless the menu already had) and closes the audio device (`ps2AudioOutSuspend`) from an SDL event watch, since SDL blocks the app's own loop while paused; 0% CPU away, everything back on return. raylib's `CloseAudioDevice` destroyed its mutex before stopping the device (an AAudio callback then aborted the app): the fork patches it in FetchContent (`cmake/patch_raylib_audio.cmake`). The activity re-hides the system bars when it regains focus.
  - Frame rates above 60 (Options → Frame rate) need frame generation, which only paraLLEl-GS renders (`Capabilities::frameGeneration`). On the hardware GS the extra presents repeated frames unevenly and the game looked as if it changed speed, so the row is hidden there. `RT_VBLANK_JITTER=1` logs how evenly guest vblanks happen.
  - Audio is rate-matched: the output callback plays the SPU2 queue up to 0.5% slower or 1% faster (linear interpolation) to hold it near 50 ms, since the guest and device clocks differ slightly and the queue otherwise grew to the 200 ms cap and dropped frames (crackle). `RT_AUDIO_STATS=1` logs underruns, drops and the queue every 5 s.
  - Performance hints (ADPF, `src/platform/android/PerformanceHint.cpp`, `RT_PERF_HINT=0` off): the VU1, GS, game and presenter threads in one session with a 16.7 ms target, reporting the busiest thread's CPU time per frame. Ten-minute race on the Thor: 60 fps, thermal status 0, CPU ≤ 70 °C, GPU at its lowest clock; the remaining dips (8% of 2 s samples under 57 fps) come from the course-select carousel, where VU1 program `entry4` keeps the VU1 thread 80% busy.
  - Another activity in front (the document picker, home) takes the window's surface: the presenter drops its Vulkan surface and swapchain when SDL reports the window minimized and makes new ones when it is restored (SDL's app background/foreground events don't reach its queue). Setup screens use `IsMouseHoveringRect(..., false)`: there is no ImGui window around them, and the implicit one clips hover tests.
  - Measuring against emulators: `scripts/android/measure.py <package> [seconds]` samples on the device (`sample.sh`, every ~0.2 s) and reports clock-weighted CPU per thread (run time x the clock of its core, GHz-equivalent) and GPU (busy x clock, MHz-equivalent); busy % alone hides governor clocks. Baseline: `build/scratch/hwgs/baseline.md`.
