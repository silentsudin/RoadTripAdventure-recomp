# VU1 programs — image, entries, and terrain path

Updated 2026-10-15. This is the SLUS-203.98 VU1 instruction image used by
Road Trip's model renderer. It is one shared image, not a program embedded in
each FLD/CAR/COURSE model packet. The longer semantic reference is
[`../vu1-microcode.md`](../vu1-microcode.md); this page records the asset-facing
facts needed by the native converter.

## Image placement (PROVEN)

The ELF's `.DVP.ovlytab` (file offset `0x1366c0`, four 12-byte records) maps
four ranges of `.vutext` into VU1 instruction memory. The overlay placeholders
are not the code bytes; each record supplies its load address and VU destination.

| ELF file offset | ELF virtual address | VU1 byte address | Bytes |
|---:|---:|---:|---:|
| `0x08f748` | `0x0028e748` | `0x0000` | `0x800` |
| `0x08ff50` | `0x0028ef50` | `0x0800` | `0x800` |
| `0x090758` | `0x0028f758` | `0x1000` | `0x800` |
| `0x090f60` | `0x0028ff60` | `0x1800` | `0x5f8` |

The reconstructed 16 KiB image (zero-filled outside those ranges) has FNV-1a
64 `0xe2868a5859386847`. `ps2_vu1_recomp --elf SLUS_203.98` independently
reconstructs that image and reaches 955 instruction pairs (6,645 timing/CFG
nodes) without an unsupported reachable instruction.

The image's first `0x80` bytes are an eight-slot jump table. `MSCAL` values
are byte addresses divided by eight, so the usual `0x0, 0x2, …, 0xe` calls
select the following targets.

| MSCAL imm | VU1 byte address | Entry | Asset role |
|---:|---:|---|---|
| `0x0` | `0x1268` | Init | camera/clip parameter setup |
| `0x2` | `0x1438` | SetupLit | object setup for lit strips |
| `0x4` | `0x1620` | LitStrip | cars, props, and lit model chains |
| `0x6` | `0x03e8` | ObjectStrip | local-space clipped strips/billboards |
| `0x8` | `0x0080` | **WorldStrip** | FLD/COURSE world-space terrain/model strips |
| `0xa` | `0x1898` | OffsetStrip | unlit/offset strips |
| `0xc` | `0x1aa0` | SkyStrip | sky layers |
| `0xe` | `0x1318` | SetupClipped | setup for entries 3, 4, and 6 |

The shared clipper begins at `0x0720` (with helpers through `0x1260`).

## How the image gets to VU1 (PROVEN)

VIF command words are `cmd = bits 24..30`, `num = bits 16..23`, and
`imm = bits 0..15` (confirmed against jak-project's `common/dma/dma.h`).
`MPG` is command `0x4a`; `num` instruction pairs follow, eight bytes each,
and `imm` is the VU instruction address. This is the command type that can
write VU instruction memory.

`DIRECT`/`DIRECTHL` are commands `0x50`/`0x51`; their `num` is a count of
16-byte GIF payload qwords. They feed GS PATH2 and **cannot** contain a VU1
program. In particular, `vifDirect` at EE `0x00226f70` emits a DMA REF tag,
then `FLUSH` (`0x11`) and `DIRECT`; it is the fog/scissor/alpha-state path,
not the program loader.

An unconstrained shape scan of 256 ELF/data files (327,663,184 bytes) found
75,527 MPG-shaped and 117,556 DIRECT-shaped words. Those are not evidence on
their own: arbitrary vertex/texture bytes produce the same top byte. Requiring
the ELF overlay metadata accepts exactly the four ranges above. The strict
`vu-dis` probe decoded long runs at every entry target; its `0x0720` start
aborts on one upper opcode it does not implement, despite the image being
accepted by the runtime interpreter/recompiler. No raw image or disassembly is
stored in this repository.

## VU1 data contract for terrain (PROVEN)

`vifCameraSetup` at EE `0x00226540` sets `BASE=0x8d`, `OFFSET=0x1ae`; VIF1
therefore alternates `TOP` between qwords `141` and `571`. Model chains upload
the output GIF tag at `TOP+0`, followed by records, then invoke entry 4 with
`MSCAL 0x8`.

WorldStrip is the terrain/courses path. Its input record is **five VU qwords**:

| qword within record | Contents |
|---:|---|
| 0 | world position |
| 1 | colour set A (RGB) |
| 2 | colour set B (`x` is alpha) |
| 3 | colour set C (RGB) |
| 4 | `s`, `t`, alpha add, spare |

The record is **not** the compact field converter packet
`[0x8000|N, 0x20224000, 0x41, materialRef] + N × (x, height, y, q)`. That is
the PMP-side terrain grammar. The bridge that builds/references the five-qword
VIF records remains to be followed; it is where the field material reference
and colour sets are bound.

The relevant WorldStrip sequence loads qwords 0–4 with `LQ`, advances the
input pointer by five, transforms qword 0, and writes three qwords per output
vertex. It makes the UV answer unambiguous:

- **UVs are STREAMED**, not generated by VU1. The final `STQ` takes `s,t`
  from input qword 4 and multiplies them by reciprocal perspective `Q`.
  The current `coord/40` planar mapping is a host-side placeholder, not an
  observed game UV rule.
- VU qword `26` is the batch offset. `vifSetBatchOffset` (`0x00226610`)
  uploads it before cell chains; WorldStrip adds `VU26.xyz` to every position.
- Camera upload puts matrices in qwords `4–18`; Init/SetupClipped load them
  into working VF registers. In the clipped world path, VU `8–11` are
  world→clip, VU `12–15` clip→screen, VU `16–18` light/rotation, and VU
  `19–23` colour/fog. SetupClipped prepares `VF1–4` and `VF13–16` for
  WorldStrip.

## Projection and XGKICK (PROVEN)

WorldStrip performs the four-FMAC matrix chain, `CLIP`, then `DIV Q, 1,w`.
It uses `FTOI0` for RGBA and `FTOI4` for screen XYZ and fog (truncate after
multiplication by 16). It stores, per vertex:

1. `STQ = (s*Q, t*Q, Q, carried word)`;
2. `RGBAQ = FTOI0(colour)`;
3. `XYZF2 = FTOI4(screen*Q, fog)`, with ADC for an outside/clipped primitive.

The output tag is at `TOP+0`; output vertices follow it, and the batch's GS
register header is at `TOP+402` (`TOP+0x192`). The program checks that
header's NLOOP, `XGKICK`s it once when non-zero, clears NLOOP, then `XGKICK`s
the strip packet. The clipper uses qword 29 as an empty EOP synchronization
kick and qwords 30–60 for clipped fan packets. Normal strips are PACKED
`ST, RGBAQ, XYZF2` (NREG 3); the common PRIM is `0x27c`.

## Open work

  builder to the five-qword entry-4 record: this establishes real `s,t`,
  texture selection, colour sets, and alpha policy for the native converter.
- Capture one field cell's VIF chain at runtime (or add a bounded parser for
  its DMA CALL target) and correlate its `TOP+1` records with the decoded PMP
  section. Do not infer UVs from position-grid regularity.
- Preserve this contract in the native renderer: apply tile origin before
  world→clip, perspective-correct streamed UVs, VU-style truncation for parity
  testing, and the material packet's texture state.
