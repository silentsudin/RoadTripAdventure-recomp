# Notes for agents

- This is a static recomp of the PS2 game Road Trip (USA, SLUS-20398) using PS2Recomp (submodule `third_party/PS2Recomp`, pinned).
- **The built app must never contain game code.** The game is recompiled and compiled on the user's machine at first launch (`src/game/GameBuilder.cpp`), and `scripts/bundle_sdk.py` ships only the recompiler, runtime headers and config. Verify with `nm RoadTrip.app/Contents/MacOS/RoadTrip | grep -c sub_00`, which must print 0.
- **Never commit game data or derived code.** That covers anything under `generated/` and `build/`, disc images, ELFs, and extracted files. `.gitignore` covers them; check `git status` before committing.
- Pipeline: `python3 scripts/pipeline.py <steps> --rom <image>`. The steps are bootstrap, tools, extract-elf, analyze, recomp, build and run. `RT_ROM` can stand in for `--rom`.
- Recompiler config:
  - Edit `config/roadtrip.base.toml`.
  - `config/roadtrip.toml` is regenerated by `analyze`. It holds addresses only and is committed.
- Runtime/recompiler changes:
  - The submodule is the user's fork (silentsudin/PS2Recomp), branch `roadtrip`; remotes `origin` = fork, `upstream` = ran-j.
  - Commit there, push `roadtrip` (the user approved pushing this branch), then commit the bumped submodule pointer in this repo.
  - Generic fixes can be offered upstream as PRs; ask first.
- The app entry point is `src/main.cpp`. It runs setup (extract the disc, build the game dylib), then `rt::game::load`, then `PS2Runtime` initialize, loadELF and run.
- Debugging: `RT_THREAD_DUMP=5` dumps guest threads; `RT_FRAME_DUMP=<dir>` saves PNGs of the window every `RT_FRAME_DUMP_SECONDS` (from `RT_FRAME_DUMP_AFTER` seconds on) (needs a window, not `RT_HEADLESS`; headless, use the test socket's `frame` command, which reads the GS output); `RT_DEBUG_UI=1` shows the debug panel. To find where the game is stuck, attach lldb to the `GameThread` thread; the game functions are native, so they show up in the backtrace.
- Game hooks go in `src/game/overrides.cpp`.
- The game's Title > Options (Vibration / Speaker / Sound Volume, which it never saved) is replaced: the hook on its task (0x2092D8) ends it as its own Exit does and opens our menu at the Sound rows (`src/game/GameOptions.cpp`). Our `[sound]` settings persist: volume and mono are applied where the audio leaves for the device (`ps2AudioOutSetMix`, after the test harness's capture), vibration writes the game's switch (0x33590E) only when it is off. `RT_GAME_OPTIONS=1` keeps the game's own screens; the regression harness sets it (test_menus checks them), and `test_options_replaced` covers the replacement.
- The town's Start menu (task 0x217148: Warp / Notebook / Radio / Items / Settings / Map; `[options]` in `config/game_state.toml`): its Settings (the game's button setup, page 5 = 0x216738) is replaced too. The page hook asks for the Pause list on its first frame, as the game's Exit does; a wrap of the list page (0x214AD0) opens our Options from the top two frames later (`OptionsRequest::Top`; Title > Options opens at the Sound rows), and closing it leaves the game on its Pause list. `test_pause_settings_replaced`.
- Radio station (the game's Pause > Radio, byte 0x177F760 + 0x12DD: 0 off, 1 PEACH FM, 2 E-RADIO, saved with the game): `rt::game::setRadioStation` (GameOptions) writes it and, while driving in town, switches the stream the game's way at the top of the next town frame (a wrap of the town task 0x2105B8 calls 0x258A48 + 0x258AF0, or 0x258B30 for Off); elsewhere the game restarts the radio from the byte. A "Radio station" row in Options (Sound, only in an Adventure) and the second screen's Radio tab use it. Test socket `{"cmd":"radio"[,"station":N]}`; `test_radio_station`.
- Driving controls and feel (`src/game/Driving.cpp`, pure parts in `DriveFeel.cpp`, `[controls]` in `config/game_state.toml`; unit test `drive_feel_test`, `tests/regression/test_driving_feel.py`):
  - Controllers → Controls: Modern (default: RT gas, LT brake, A jet, RB/LB wings, Y horn & lights, B view, Back navigator; keyboard-only players keep Classic) / Classic (the game's own) / Custom (the Driving controls page: select an action, press a control; allowed buttons go into the game's masks, others are bound in our input layer; Custom's layout is kept when switching away). In Modern and Custom, holding the brake at a standstill reverses. The scheme's layout is written into the game's own setup while driving (0x21A820 wrap), so it saves with the game. The page draws controls as the pad in hand shows them (`th::control`, `rt::input::bindingGlyphs`). The only game text naming driving buttons (the wing set's "press the L1 / L2 button", 0x326EAD) is rewritten to player 1's wing buttons.
  - Analogue triggers (Driving controls page, default On): gas = the Gas bit pulsed (duty 0.5 + 0.5 x trigger: the engine hardly moves below half duty) under a speed cap of trigger x the learned top speed (some cars accelerate as fast at 65% duty as at full); brake = the ramp at car + 0x1FE held at ceil(32 x trigger).
  - Controllers → Vibration: Dynamic (default; engine, the ground, gear changes, brakes on the left trigger, landings, wall scrapes, the game's knocks from 0x20ACB8 graded by pattern/strength; both motors and the trigger motors) / Classic / Off, above Strength; each change plays a short sample. `RT_RUMBLE_TRACE=1` logs the game's rumble calls.
  - What the car reads (`[controls]` in `config/game_state.toml`, probed on the Thor over five Quick Race courses): the ground is the wheels' contact words (car + 0x1A8..), named by their material bits 8-10 (`feel::surfaceOf`: asphalt, dirt/sand, grass, snow, ice, boards/brick/panels, water), each with its own grain. Contact words are never -1 in the air (only for a point pushed into a wall): airborne = the three body points' fall speeds (car + 0x1C0/0x1C4/0x1C8) all above 0; the landing thump goes by the fall at touchdown (`feel::landingStrength`), and the game's own pattern 1 is that landing per point (strength = fall / 16). Patterns 3/4/5 are wall scrapes, not rough ground: 4 left side, 3 right, 5 front (the trigger on that side pulls). The old "skid" byte at +0x1C4 was a fall speed. Test socket `driving` reports `surface`, `airborne` and `scrape` per port; `test_surfaces_and_wall_scrapes`.
  - Schemes and analogue are off under `RT_TIME=virtual`, `RT_MOVIE_RECORD` or a movie/script (the game's own layout, buttons only) unless `RT_CONTROL_SCHEME=modern|classic|custom` / `RT_ANALOG_TRIGGERS=1`. Test socket `{"cmd":"driving"}` (actions, analogue, reversing, dynamic rumble per port; `scheme`, `action`+`button`, `analog`+`gas`/`brake`); `sdlpad` takes `lt`/`rt` 0..1 and reports the motors the app asked of the virtual pad.
- In-game menu (`src/ui/PauseMenu.cpp`, look in `src/ui/Theme.cpp`): Guide, Back+Start held 0.3 s, Esc, F3 or Android's back opens it and pauses the game (`ps2_test::setPaused`). The panel never changes size or position as the focus moves (picture rows only lift the scrim a little). Options live in `settings.toml` in the data directory (`src/settings/`); options a device can't use, or that aren't built yet, are hidden.
  - Screenshots headlessly: `RT_MENU_SHOT=<png> RT_MENU_PAGE=root|display|graphics|controllers|device|buttons|quit|reset RT_MENU_AT=<vblank>`; with `graphics`, `RT_MENU_ROW=<label>` selects that Options row.
  - Critics: have `choroq-style-critic` and `jobs-ux-critic` (`.claude/agents/`) review screenshots after UI changes.
- Save states in the menu (Mac and Android; `src/states/StateSlots.cpp`, `PauseMenu.cpp`): Save state / Load state rows only in an Adventure or a race of the player's, no movie, and a GS that can save (`Capabilities::saveStates`: every GS now). A refused save/load reports the pending request's blockers and loop tops (`ps2_save_state::pendingBlockers`). Thor, Quick Race, real time: save and load each after 1 vblank, ~95 ms while the menu holds the game, 6.4 MB per slot. Four slots `<data>/states/slot<N>.rtstate`, each with a PNG of the moment in the header (`thumbnail`, taken through `ps2_test::requestAppFrameCapture`). While the menu holds the game, a save/load lets vblanks through one at a time (≤120) until a savable point; a save refused mid-VU1 is retried. A menu load marks the memory cards changed (`ps2_save_state::markMemoryCardsChanged`: the next sceMcGetInfo returns -1) and closes the menu; every load flushes the host audio queue. Test socket: `state_slots`, `state_slot` (op save|load), `state_slot_status`; `test_state_menu.py`.
- Agents in `.claude/agents/`: `bug-tester` (runs the regression suite, triages), `perf-profiler`, `reverse-engineer`, `release-guard` (run before commits/pushes), plus the two UI critics.
- Widescreen (Options → Aspect ratio, HUD position):
  - The game hook in `src/game/overrides.cpp` widens the 3D by narrowing the player cameras' projection X. It wraps 0x21F698 and its resume points, and keeps the tile-cull points (0x29CF40) widened.
  - The GS frontend's `WideLayout` (`gs_wide_layout.cpp` on the fork) narrows the HUD in driving frames, and marks 2D-backed screens, which the presenter shows at 4:3.
  - HUD position "edges": HUD units are placed at the end of each packet; primitives of one packet that touch or overlap form one element, anchored by its own centre (the town dialogue window is ~70 sprites in one PATH2 packet; anchored per third it came apart and looked stretched). Scissors take the anchor of the unit before them.
  - The 2D verdict is decided at each frame's first draw: 3D first = wide at once; a full-screen textured picture first (TBP at or above 0x1A40, not a post-pass) = 4:3 at once (the title fades in from its first frame); a full-screen untextured fill (the black behind "NOW LOADING...") = 4:3 from the second such frame in a row; anything else votes as before. `RT_WIDE_DEBUG=1` logs verdict changes and frames shown unlike their kind. A frame whose first draw is a semi-transparent untextured full-screen fill (a fade over the previous picture) keeps the verdict it had, and is handled as driving when wide ("NOW LOADING" keeps its shape). Each frame buffer keeps the verdict of the frame drawn into it (`m_wide2DByFbp`, stamped at vertex kicks), and `lastFrameWas2D()` answers for the buffer on display (the next frame's first draw often came before the presenter latched the shown one: one wrong frame at every change). `RT_WIDE_DEBUG=2` logs each frame's first draw. Only the game's own Settings page (behind `RT_GAME_OPTIONS=1`) still shows stretched. Test socket `{"cmd":"wide"}` (frame_2d, driving, k); `Game(settings=...)` writes settings.toml; `test_widescreen.py`.
  - Frame boundaries come from the game's clear stub (`GS::markFrameStart`).
  - Run fast path (`GS::fastPath1Run`, backends with `WantsRuns`: the hardware GS): a PATH1 PACKED tag that is a plain triangle strip or list (RGBAQ/ST/UV/XYZ(F)2/FOG, one vertex a loop, no ADK, no queue carried in, no debug recorders, no frame skip, no classifier verdicts) is parsed in one loop and handed over as one `SubmitRun` (each vertex converted once); the front end's state is left as the per-register path leaves it. `RT_GS_RUNS=0` off.
  - Without a packet mirror (hardware GS), PATH1 packets skip the classifier once the frame's kind is known and its HUD hasn't begun (`WideLayout::plainPath1`: every vertex Scene, or Ui on a 2D screen, `defaultClass()`); they were copied and parsed for nothing.
  - Unit test: `wide_layout_test`.
- Progressive fields (Options → Interlacing: Off, the default; `RT_PROGRESSIVE_FIELDS=0|1` overrides it):
  - The game draws 640x224 fields and moves every other one down half a line (sceGsSetHalfOffset at 0x26F340 and 0x26F3C8, `halfoff` = the field parity). The hook in `overrides.cpp` forces `halfoff` to 0.
  - The pgs backend hides INT/FFMD from paraLLEl-GS, so the field is scanned out as a progressive double-strike picture.
  - `VSyncInfo::progressive_field_scanout` takes twice as many lines as columns from the super-samples: 2x and 4x give 640x448, 8x and 16x give 1280x896 (`shaders/scanout_sampling.h` on the paraLLEl-GS fork).
  - A real 448-line frame can't fit in VRAM: textures start at block 0x1A40, right after the 224-line buffers and Z.
  - The regression harness pins `RT_PROGRESSIVE_FIELDS=0` so the goldens keep the original fields; `test_progressive_fields.py` covers the progressive path.
- Texture dumps and HD packs (Options → Texture pack; `[textures] dump` and `pack_anisotropy` in settings.toml, for pack makers and tuning; `gs_texture_tools.cpp`, the pgs backend's `textureToolsLocked`, and the readback/prediction hooks in our paraLLEl-GS fork):
  - a texture is the whole image the game uploaded (host-to-local transfer at the TEX0 base, same format), not the part a draw samples: the game cuts sprites out of atlases with REGION_CLAMP (the HUD font is one 512x384 4-bit upload). With dumps or a pack on, paraLLEl-GS tracks uploads (`GSInterface::uploads`) and decodes a REGION_CLAMP draw inside one as the whole upload (`decode_desc`, its own cache key, no sampler feedback), while the draw keeps its own descriptor and sampler region. Widened draws skip the render-pass texture memo, which the image's invalidations can't reach. A draw over pages the game has rendered to isn't widened. `test_texture_pack` checks that dumping changes no pixel.
  - with either on, paraLLEl-GS copies each newly decoded texture (RGBA8 with the palette applied; PS2 alpha, 0x80 = opaque) back to the host. A worker names it by an FNV-1a hash of its decoded pixels: the same texture gets the same name across runs, wherever it sits in GS memory, and a palette swap is a different texture.
  - dumps go to `<data>/textures/dumps/<hash>_<W>x<H>_psm<NN>.png` (`rt::paths::texturesDir`; on Android the app's external files, `Android/data/<package>/files/textures`, which a computer reaches over USB; an older private `files/textures` moves there once; `RT_DATA_DIR` keeps it under the data directory). A pack is a folder in `<data>/textures/packs/` of PNGs whose names start with the 16-digit hash, at any size (alpha in PNG terms).
  - a replacement is created once per content (sampled only, no storage usage: paraLLEl-GS addresses it by the original texture's size and keeps it out of its image pool). It is bound by the texture's stable key (the cache key without the palette instance, `TextureDescriptor::stable_key`), because Road Trip reloads palettes every frame and paraLLEl-GS decodes such textures under a new cache key each time. Each decode still reads back and re-checks: a description that decodes to something else drops its prediction.
  - replacements get a full mip chain and are sampled with analytic texture-coordinate gradients through a trilinear/anisotropic sampler (`BINDING_SAMPLER_ANISO`, the `TEX_INFO_REPLACED` path at the top of `sample_texture` in `ubershader.comp`). `pack_anisotropy` sets it (1–16, default 16; no menu row: it costs next to nothing).
  - `RT_TEXTURE_DUMP=<dir>`, `RT_TEXTURE_PACK=<dir>` and `RT_ANISOTROPY=<n>` override the settings. Headless, the GIF path services the readbacks when no vsync has for 50 ms.
  - clamped textures sample through clamp-to-edge variants of that sampler (bindings 27–29), so pack images don't bleed in their far edge at any mip level. On clamped axes (CLAMP and REGION_CLAMP) a replacement's coordinate is also kept inside the region by half a pack texel or half the pixel's footprint (from the unclamped gradients), whichever is larger: clamped at the region's edge, the filters took half their weight from the next sprite of the atlas (the PS2 sampled point-wise and never read it), which drew lines beside HUD sprites (the speedometer, TOTALTIME). Same in the hardware GS's `F_REPLACED` path (`textureGrad` with the unclamped gradients). Lines that remain with an AI-upscaled pack come from the pack: the model gives alpha to texels that are fully transparent in the original (upscale alpha separately).
  - the worker remembers contents with no pack image and no recolour (`m_knownMiss`, cleared when the pack or the recolour candidates change), so textures the game rewrites every frame (a scrolling one cycles through a few contents) skip the index pattern and the fit (~5% of a core on the Thor).
  - switching packs (or to none) drops every replacement and prediction on the main and shadow GS and invalidates the whole texture cache (`GSInterface::drop_texture_replacements`), so textures decode from GS memory again. The Texture pack hint shows how many of the pack's images the game has used (`PgsControl::texturePackStats`).
  - HD packs (the main use: every dump upscaled): replacement images are created at most 24 MB per frame (`kCreateBytesPerFrame`, pending ones wait), and kept within a memory budget (2 GB, `RT_TEXTURE_PACK_BUDGET_MB`): paraLLEl-GS reports the replacements it binds (`collect_used_replacements`), and images not drawn for 2 s are evicted oldest first down to 80%, then the texture cache is invalidated once (predictions rebind the rest at once). A 4x pack of every dump (6,499 images, 13 GB if all resident) holds 60 fps in a race with 254 images, 1.25 GB; loads cost up to ~4 ms a frame. `[textures] pack:` log lines every 5 s give images, MB, pending, evictions, worst ms per frame and palette matching.
  - ASTC cache (hardware GS, where the device samples ASTC 4x4; `gs_texture_pack_cache.{h,cpp}` on the fork, Arm's astc-encoder 5.7, Apache-2.0): each pack PNG is encoded once (PS2 alpha, a box-filtered mip chain, fast preset) to `<data>/textures/cache/<pack>/<hash>.astc` with the PNG's size and time (an edited image is encoded again), and loaded from there with no PNG decoding (decoding a 4x pack's images when entering a building took ~1.5 cores on the Thor) at a quarter of the memory (the bar's 436 images: 356 MB, 1,424 MB as RGBA8; lockstep frames match the PNG path within 0.5 levels on average). Encoding never runs during play: at start ("Getting <pack> ready", `prepareTexturePack` in `main.cpp`, every core: the user's 4,683-image 4x pack in 215 s, 2.5 GB; "Play now (finishes next time)" ends it, the rest loading from PNG meanwhile), and when a pack is chosen in Options while the menu holds the game (`src/textures/PackPrep.cpp`: progress in the row's value, the hint and a bar; closing the menu stops it, with a notice that it finishes at the next start; finishing while the menu is open gives the pad a short pulse, `sampleVibration(2)`, and the hint says Ready). paraLLEl-GS keeps the PNGs. `RT_TEXTURE_ASTC=0` loads the PNGs; `RT_TEXTURE_PREPARE=0` skips the start's conversion.
  - other palettes of a replaced paletted texture (fades, flashes: Road Trip reloads palettes, and paraLLEl-GS keys by register state, so a fade keeps the stable key): `TextureTools` keys paletted textures also by index pattern (colour classes by first appearance) and, on a miss, fits an affine colour map (4x4 + offset, least squares, within 3 levels) from a replaced texture with that pattern to this palette. The pack image is then bound with `TEX_INFO_RECOLOR`, the map in the `texture_recolor` UBO (binding 30, slot in TexInfo flags >> 8). Arbitrary palette swaps don't fit and need their own pack image (they are dumped). `RT_TEXTURE_RECOLOR=0` turns it off; `RT_TEXTURE_RECOLOR_TEST=swap` recolours every match red/blue swapped (test hook).
  - `rt_audio_extract <disc dir> <out dir>` (`tools/audio_extract.cpp`) decodes the disc's VAG streams (PlayStation ADPCM) to WAV, `_L`/`_R` pairs as stereo: SOUND/1CH-3CH, about an hour each at 12 kHz (1CH's channels are identical). The sequenced music and effects (TSQ sequences + TVB sample banks, Takara's own formats, played by SNDMOD.IRX) are not decoded.
  - `rt_texture_extract <disc dir> <out dir>` (`tools/texture_extract.cpp`, `src/textures/Extract.cpp`) writes every texture on the disc in seconds, under the same names: it replays each file's GS upload packets (BITBLTBUF..TRXDIR + IMAGE) into a GS memory image (PS2Recomp's `ps2_gs_memory.h`) and decodes them as paraLLEl-GS does (`upload.comp`: CSM1 palettes, 16-bit colour `<< 3`, TEXA with AEM on, which is what Road Trip sets). A texture's palette is the one a TEX0 in the file names, else the upload right after it. A 256-colour palette after a 4-bit texture gives 16 banks (CSA); banks other than 0 go to `palette-variants/`. `sources.csv` says where each came from. Textures the game builds or recolours in code (HUD colour flashes, palette fades) are only caught by runtime dumps.
  - `test_texture_pack.py` dumps a race, makes a tinted 2x pack from those dumps in a temp dir, and checks that the pack shows, goes and comes back when switched while running, and that anisotropy changes it.
- Hardware GS (`RT_GS_BACKEND=hw`, `include/runtime/gs/gs_hw_backend.h`, `src/lib/gs/hw/` on the fork): draws the frontend's primitives with the Vulkan graphics pipeline on the presenter's device (or its own, headless), for what Road Trip does, not the whole GS. Lighter than emulation is the goal (`build/scratch/hwgs/baseline.md`: ARMSX2 vs us on the Thor).
  - Spec: `RT_GS_STATE_SURVEY=<file>` (`%p` = pid) counts every distinct draw state and transfer; `scripts/hwgs_survey.py` runs the suite with it and writes `build/scratch/hwgs/states.md`.
  - Render targets stay on the GPU (RGBA8 at the render scale, vertical scale doubled for progressive fields, alpha stored as A/128 so As/Ad blend factors are exact); one D32F depth image per ZBP. Textures are decoded on the CPU from local memory (palette applied, cached by page versions + palette; a paletted decode makes its palette once and looks texels up in it); a texture inside a render target (the post-pass, the loading blur) samples a snapshot of it; DATE reads that snapshot at the pixel.
  - The GS thread records and submits at buffer flips; `Present` records the rest and scans out. Consecutive draws merge when the frontend's draw-state serial (`GSPrimitiveBatch::stateSerial`, bumped by any non-vertex register write) is unchanged, else when `sameDraw()` finds the states equal field by field (never memcmp: padding holds garbage). Vertex data goes through a ring of 8 fenced buffers; uploads are hashed per page, so re-uploading the same pixels (the game does it every frame) invalidates nothing. Alpha test and alpha mode are specialization constants. Render scale: the supersampling setting (1/4/16 = 1x/2x/4x); `RT_GS_SCALE=<n>` wins over it. `RT_HWGS_STATS=1` logs batches, passes and snapshots per present and what breaks batches.
  - Shaders: `hw/draw.vert|frag`, rebuilt into `hw_spirv.h` by `hw/compile.py` (glslc).
  - Parity with paraLLEl-GS: scanout matches it (size and the alternate fields' half-line offset with interlaced fields); 2D (sprites, flat triangles, HUD) snaps to whole GS pixels with texture coordinates moved to match, and above 1x takes texture coordinates, colour and fog at the GS pixel's sample point (horizontal only with interlaced fields; the mode from `RT_PROGRESSIVE_FIELDS`); destination alpha test through the stencil buffer (Z becomes D32S8; a batch now sees the alpha its own earlier triangles wrote: shadows no longer darken twice, `RT_HWGS_STENCIL_DATE=0` for the old test, `hw/date_stencil.frag`). The stencil is set from the target's alpha MSB once per run of DATE draws, which keep it in step; it is set again only after another alpha write, a new or loaded Z buffer, or another target's prepass (`Target::stencilSerial`). Set per draw (snapshot + prepass), Q's Factory's 39 car-shadow draws a frame cost 57 passes a present and GPU 82% at 120 Hz on the Thor; now 6 passes, 55%. Snapshots for DATE are also reused while no draw has written alpha (`alphaSerial`); alpha-test fail modes where Z can't change the colour draw every pixel's common write first, then what only passing pixels add (the race map's marker over the track). Debug: `RT_HWGS_SNAP`, `RT_HWGS_BATCH_LOG`, `RT_HWGS_DROP`.
  - Pipelines: a persistent Vulkan pipeline cache in `<data>/cache/hw_pipelines.bin` (saved when warm-up ends, then every 10 s), and a list of the states the game draws: built in (`hw/hw_pipeline_states.inc`, 256 states recorded on the Thor in town, a field area, quick races and menus, with and without TAA's motion attachment and texture packs) plus `hw_pipeline_states.txt` there (every state drawn is recorded). The known states compile on a worker at startup (`hwPipelinePrep`; `RT_HWGS_WARMUP=0` turns it off); a first launch used to compile ~100 pipelines synchronously on first use, 8-25 ms each. On Android a first run ends with the setup step "Preparing graphics", and a later start shows "Starting Road Trip" when the cache can't serve the list (driver or app update): the game never starts before it is done (no background compiles during play), after a silent wait of up to 1 s, at least 0.8 s on screen with fades, and gives up after 20 s (or 5 s without progress). `RT_SETUP_TEST_GRAPHICS=1|2` shows the first-run step / the startup screen for reviews. Thor: 256 pipelines in ~0.45 s; warm start 0 stalls.
  - The map layer for the second screen is published when drawing moves to the other frame buffer (the GS thread can run a frame behind the EE, so a Present could land mid-map; publishing at Present made the map flash). For the hardware GS the presenter's `end_frame` runs outside our device lock (`RT_PRESENT_UNDER_LOCK=1` restores it): the Adreno driver sleeps in `vkQueuePresentKHR` for 5-15 ms, which held the GS thread out. On Android presents go out on a thread and a Vulkan queue of their own (`RT_PRESENT_THREAD=0` off; opt-in elsewhere with `=1`): a device factory asks for one more queue in the graphics family (used only when one exists: on Granite's own queue the thread would need Granite's queue lock, which `wait_idle` holds while it waits), Granite's present/acquire/swapchain/wait-idle entries are wrapped, the main screen's and the second screen's presents are copied (pNext chain included) to the thread, and a present's result comes back with the next present to that swapchain (out-of-date rebuilds one frame later). Each swapchain has its own mutex; swapchain destruction and device waits let queued presents out first; `render()` waits, holding no lock, for the previous frame's presents (no backlog, pacing unchanged). Thor, Peach Town main roads at 60 Hz: 52.2 → 59.7 fps (3 of 81 half-second windows under 57, was 40); field area 60.0.
  - Motion vectors (TAA): with `PgsShared::wantMotion` the frontend puts MotionTracker's per-vertex motion on `GSVertex::motion` (it asks with `WantsVertexSideband`), and the backend draws it into an RG16F attachment beside each target's colour (draws without blending or with Cs*As + Cd*(1-As), the motion output carrying the colour's alpha), copies the scanned-out part to `PgsShared::motion` and clears it before the next frame draws. Depth: where the HUD starts (`SnapshotDepth`), the 3D's D32F depth is copied as raw 24-bit GS Z, the scanout's part (`hw/depth_copy.frag`), to `PgsShared::depth`, as paraLLEl-GS gives it (`RT_SHOW_DEPTH=1`). `RT_HWGS_MOTION=1` turns motion on headless; `RT_HWGS_STATS=1` counts vertices with motion.
  - UI mask (post-processing spares the HUD): with `PgsShared::wantUi` the backend asks for the widescreen classifier's verdicts (`WantsVertexSideband`; each `GSPrimitiveBatch` carries `vertexClass`, matched to the packet's vertex kicks) and draws the UI-class triangles into a mask the scanout's size at Present (whole sprite rectangles, not per texel). `RT_SHOW_UI=1` shows the mask in place of the picture (either GS).
  - Texture dumps and packs (`hw/gs_hw_textures.cpp`, `HwTexturePacks` over the same `TextureTools`): with either on, each batch's texture is named as paraLLEl-GS names it (`effectiveRect`, the port of `compute_effective_texture_rect`; a REGION_CLAMP draw inside a tracked upload stands for the whole upload) and decoded on the CPU once per content for the tools. A race dumps every name paraLLEl-GS dumps (281 of 281) plus a few it skips (the 640x448 title picture), so packs work on both. A replacement is drawn with `F_REPLACED` (implicit derivatives, the anisotropic samplers, clamped axes clamp to the edge) and recoloured with `F_RECOLOR` (the map in the binding-2 UBO). - Recompiled EE functions take `rdram` and `ctx` as `__restrict` (they never overlap): otherwise every guest store (a `uint8_t*`) made the compiler reload and re-store guest registers around it. On Android the recompilers live in the app, so `bundle_sdk.py --android` hashes their sources into the kit's build id (a recompiler change rebuilds the game on launch; it didn't before).
- VU1 microcode is recompiled to lean code (the default; the game builder passes `--split`: one function and file per microprogram, which compile in parallel and in linear time, where one function of all eight took minutes on a phone): straight-line code per explored node, stalls as constants, Q/P landing where the explorer saw them, flags only where read, an XGKICK copies the packet at the kick; it deopts to the interpreter when timing isn't static. `vu1_replay` checks it against the interpreter (`--split`, `--reference-interp`). `PS2X_VU1_RECOMP_FLAGS="--interp-steps"` (read by `ps2_vu1_recomp`, so through the game builder too) builds the previous interpreter-step code for A/B. Pairs run on cached registers (`LeanR` in `ps2_vu1_native.h`, written through to `VU1State` so deopts and fallbacks still work), clamps skipped where a dataflow pass proves the operand already clamped, FTOI saturation vectorised: entry4 (the course carousel, ~12k runs a frame) 39% cheaper, the others 27-44%; on the Thor the carousel holds 60 at VU1 49% (was 80%), and the VU1 parts compile ~3x faster. `vu1_replay` has `--bench` per program, `--only PC`, `--fuzz N[,rate%]` (perturbed and special floats against the interpreter), `--as PC`, `--write-capture`/`--strict-flags` (build against build). The per-run FPCR switch (~27 ns, ~15% of entry4) could be hoisted around consecutive runs at the call site.
- EE reads of GIF/VIF1 registers wait for the GIF/VIF1 worker only (`PS2Memory::syncGifVif1`, `t_syncWorkerOnly`): Road Trip polls VIF1_STAT and GIF_STAT every frame, and waiting there for the GS thread too serialised the EE with the whole GS stage (~5 ms a frame; Thor field drive 48.8 → 59.0 fps, and the 30 fps lock that a menu pause could start or clear went with it). Every other sync (privileged GS registers, CSR, the FIFOs) still waits for the GS thread to finish what the worker handed it: a display switch at vblank must not overtake queued drawing (half-drawn frames flashed when it could). `RT_VIF1_READ_WAITS_GS=1` restores the old wait for A/B.
- The GIF/GS hand-off reuses packet buffers (`GifArbiter::recycle`), and a waiter is woken only when the lowest target it waits for is reached. Lean VU1 kicks are copied once, into a pooled queue buffer handed over as it is (`PS2Memory::submitGifPacketOwned`; a deopt mid-transfer copies it back for the interpreter). The GS thread prefetches the next packet while parsing one (the first touch of data written on the VU1 core was ~8% of it). Batch lists come back through `GifArbiter::recycle` and go out again with `takeBatch` (each hand-off left the list empty, and regrowing it 1, 2, 4 .. 32 cost the VU1 thread ~9%). VIF1 DMA chains are moved into the worker's jobs, not copied, and their buffers come back for the next chain (`takeChainBuffer`: ~18% of the game thread). `drainInto` keeps the queue's capacity when the batch takes its buffer (it regrew from nothing every batch: ~3% of the VU1 thread). Its queue ordering allocates nothing when already in order (`std::stable_sort`'s buffer after every VU1 program cost a tenth of the VU1 thread on Android, in malloc's lock).

- IOP native stand-ins (`ps2xIOP/include/ps2x/iop/iop_native.h`): a module's own routine is replaced by host code, bound when a module whose name matches loads (or a state loads) and its code hashes as registered (relocated words left out; no game code in the repo). - `MotionTracker::onMscal` (every VU1 run) takes its mutex only for setup runs (the object lists); vertex runs read the active object lock-free, use its inverse computed once per object (a batch offset applied as T^-1 C^-1), and reuse the last context id when nothing changed, so the VU1 thread sends a marker packet only when the id changes. Before, each of the thousands of runs a frame locked, inverted a double 4x4 and pushed a 32-byte packet through the GIF queue: Thor, circling in a field area at 120 Hz, VU1 thread 47% -> 33%, process CPU 158% -> 137%. `packetMotion` uses prev * C^-1 as one matrix; for the primitive backends (hardware GS) each vertex's motion is worked out at its kick (`MotionTracker::vertexMotion`) instead of in a pass over the packet. The VU1 thread keeps the VU's float mode (FPCR round-to-zero + flush) for good, so runs neither switch nor restore it (`RT_VU1_STICKY_FPCR=0`: per run). Runs without a context are tagged 0 (no motion), and a part turning more than 10 degrees a frame (wheels) moves by its translation only (`RT_MOTION_SPIN=0` off).
- `MotionTracker::context()` (once per PATH1 packet on the GS thread) takes no lock: `m_nextId` is atomic and publishes each ring entry, and `context()` re-checks it after copying (an entry overwritten meanwhile is refused). The VU1 thread holds the tracker's mutex through `onMscal`, and the GS thread waited on it 44% of the time: Thor, Peach Town at 120 Hz 48 -> 60 game fps (120 shown), the course carousel 41-57 -> 60, a 10-minute session 60.0. Supersampling on the hardware GS is the square root rounded down (1, 2 -> 1x; 4, 8 -> 2x; 16 -> 4x); the row shows the render size there (`Capabilities::hardwareGs`).

The presenter acquires swapchain images with the device lock released when the backend submits only under it (`PgsShared::submitsUnderLock`, the hardware GS): holding it there starved the GS thread at 120 Hz (30 fps). Re-rendered frame generation alone doesn't ask for per-pixel motion or depth (only the motion tracker's per-vertex motion; the side data stays on for the UI mask), so neither GS draws the motion attachment or takes depth snapshots for it. FSR 1's EASU runs in 16-bit arithmetic where the device has shaderFloat16 (`post/fsr_easu_h.frag`; 0.81 ms a present on the Thor at 401 MHz against 1.49; `RT_FSR_FP32=1` keeps 32-bit). `RT_GPU_TIMES=1` logs GPU time per stage (`=2` adds the hardware GS's render passes by target, real and shadow, its snapshots, scanout and UI mask: in town at 120 Hz its own drawing is ~1.5 ms of GPU a real frame, the post-processing ~3.6 ms; the "recording" spans include waits and overstate it) (GS recordings real/shadow, the presenter's post for real and generated frames, flicker blending, EASU, the swapchain pass) every 2 s. Thor, 35 s of race at 120 Hz, 2x, FSR 1 (`RT_PERF_LOG=1` logs every half-second window): 59.6-59.9 fps, 0-6 of 70 windows under 57 (single slow frames, not load; GPU 63% at 401 MHz, which the governor keeps); 60 Hz: 60.0. The vertex ring is 32 slots (shadows upload their own); `RT_HWGS_STATS=1` logs shadow recording time and vertex-ring waits.
  - objects are matched to last frame's (`MotionTracker::matchPrevious`): the object at the same draw position if it is within 3 world units, else the nearest within 3 units, with orientation breaking ties. Measured at a race start: draw order is stable for 93% of objects, which move 0.5-0.75 units a frame; grid cars stand 10-30 units apart, a car's wheels sit 0.7-1.4 units from its body and turn a long way each frame. A 40-unit radius mixed up neighbouring cars and a car's own parts. Shadow frames keep Z as the game computed it, so coplanar decals keep equal depths.
  - interlace flicker blending (progressive fields only, `post/flicker.frag` and `flicker_cut.frag`): pixels that alternate between two pictures, and hard cuts, are blended as an interlaced TV would show them. The loading screen alternates the blurred menu and black every frame.
  - on macOS the Vulkan presenter presents through Metal (`gs_metal_present.mm`): it renders into an offscreen BGRA8 backbuffer (a ring of three) under the device lock, then, after releasing the lock, copies it into a drawable of the window's `CAMetalLayer` on MoltenVK's own Metal queue, with `presentDrawable:atTime:`. Presented handlers feed the adaptive lead. MoltenVK's swapchain fetched its drawable lazily under the lock the GS needs, and at two presents per frame that cost game frames. `RT_METAL_PRESENT=0` uses the Vulkan swapchain, as other platforms do.
  - the app reaches the window, keys and time only through `src/platform/Host.h` (SDL3), so both presenters work.

- Upscaler plugins (Windows; `plugins/upscalers`, ABI `ps2xRuntime/include/runtime/gs/rt_upscaler_api.h`, host `gs_upscaler_plugins.{h,cpp}` and `upscalePlugin()` in the presenter, modelled on `upscaleArmAsr`): FSR 3, DLSS and XeSS are DLLs beside `RoadTrip.exe` behind a C interface, loaded with LoadLibrary (`RT_UPSCALER_PLUGINS=<paths;...>` overrides for tests). **DLSS's and XeSS's licences forbid linking their SDKs into a GPL program, so they only ever live in `rt_vendor_upscalers.dll` (built with MSVC, shipped as a separate add-on zip), never in the app or its main zip.** `rt_fsr3.dll` (llvm-mingw; AMD FidelityFX SDK **1.1.4**, MIT, `ffx-api` with the signed `amd_fidelityfx_vk.dll`: the 2.x SDK is DX12 only) ships in the main zip. `scripts/fetch_upscaler_sdks.py` fetches the pinned SDKs; the options row appears only when the plugin works on the GPU (`Capabilities::upscalerPlugins`). The presenter loads the plugins first, adds their instance extensions in `SdlPlatform` and their device extensions in `PresentDeviceFactory` (filtered by the driver; the device is made by our factory whenever plugins exist), then `RtuApi::init`. - Disc images: `IsoReader` reads .cue/.bin, .iso and .chd (libchdr, FetchContent; CD and DVD CHDs, the data offset found by the volume descriptor at sector 16). A picked image is hashed whole against the good dump (`verifyImage`, `RomInstaller.h`; Redump disc 27678 lists the .bin's SHA-1): .bin 236b902a…, .iso (its 2048-byte sectors) 62a9b61f…, CHD data 3db60fb0… (`chdman createcd` from the .bin) or the .iso's hash (`createdvd`). A CHD is decompressed in full (libchdr checks each hunk's CRC) and compared with its own header record first: damaged = mismatch, intact but made another way = unverified. Mismatch/unverified asks before going on (Android: "Use it anyway"); `--rom`/`RT_ROM` only logs it. The boot ELF check stays the hard gate. `iso_reader_test` (ctest, `RT_ROM=<image>`) covers all four forms.

- Save states (task #28; plan and decisions in `docs/save-states.md`; no menu yet): `runtime/ps2_save_state.h`, `Kernel/SaveState.cpp` (chunks, one `serializeState` per subsystem across the runtime, IOP, SPU2, HLE stubs and GS; the app's GAME chunk in `src/game/overrides.cpp`) and `Kernel/SaveStateFile.cpp` (`<data>/states/*.rtstate`: header with the game's ELF CRC, versioned chunks with hashes, zstd; written on a worker, temp file + rename; loads checked off the game thread and rolled back on failure, with a reason: not a state, damaged, another game, newer or older version, a resume PC this build doesn't have). `ps2xIOP/include/ps2x/state_archive.h`: field-by-field archive (structs refused at compile time), unordered maps rebuilt in saved order. Snapshots only at the scheduler's loop top when `EeScheduler::canSnapshot()` allows (continuations are tagged `EeContinuationKind`; memory-card I/O blocks for ≤2 vblanks). Deterministic save→load→replay in race, town and loading on the CPU GS and paraLLEl-GS, in the same and a fresh process (44 MB raw, ~6 MB file, ~15 ms on the game thread). paraLLEl-GS supersamples aren't saved (one frame differs slightly after a load). The hardware GS saves local memory, CLUT and transfer state as the CPU GS does (its CLUT in the CPU GS's slot, so any GS can load it) plus an "HWG1" part: the texture tools' upload extents and the real frame's render targets and Z, raw at the render scale (the GS thread's queue is recorded first). Targets are needed for exact replays: the game blends with what the buffer held, and redrawn targets still differed after 300 frames. On load the queue is dropped, page versions bumped (textures decode again), shadow frames warm up again; targets saved at another scale are blitted (Z starts empty); a state from another GS loads with empty targets. State hashes skip the targets (`StateArchive::setDigest`). 44 MB raw, ~12 ms on the M3 Max.   - Audio is rate-matched: the output callback plays the SPU2 queue up to 2% slower or 1% faster (linear interpolation) to hold it near 50 ms, since the guest and device clocks differ slightly and the queue otherwise grew to the 200 ms cap and dropped frames (crackle). `RT_AUDIO_STATS=1` logs underruns, drops and the queue every 5 s (and the slowest playback rate). The queue is smoothed over ~0.1 s, ±2% proportional with a slowing-only integral trim (at most 2% slower: frame skip keeps guest time real), and priming refills to 3/4 of the target. When the queue runs dry, playback holds silence until it is back to half the target (and `ps2AudioOutFlush` re-primes), so it doesn't underrun again and again while it refills.
